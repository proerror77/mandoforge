# Stage 2 Gap Audit

This audit maps the PRD v2 Stage 2 target to the current repo state. It is intentionally strict: reserved boundaries count as groundwork, not completed product capability.

## Status Summary

| Stage 2 area | Current state | Gap |
| --- | --- | --- |
| Multi-tenancy org/team/project | Single default tenant remains the runtime scope, but `organizations`, `teams`, `projects`, `memberships`, and `tenant_invitations` tables plus Admin-only hierarchy APIs are implemented. Organization rows persist `owner_subject`; new organizations default ownership to the creating admin subject, and ownership transfer is exposed through audited Admin API/UI paths that fail closed for archived organizations. Organization/team/project archive APIs now persist `archived_at`, write audit records, and fail closed when archived scopes or archived ancestors are used for new teams, projects, memberships, invitations, or scoped access checks. Archived empty organizations can be deleted through audited Admin API/UI paths; deletion fails closed for active organizations or archived organizations that still have teams, memberships, or invitations. Admin bootstrap provisioning can create an organization plus optional team/project and owner membership in one audited path. Admins can create/revoke scoped invitations, invitees can accept pending token-bound invitations without a pre-existing role, acceptance creates the scoped membership, and invitation create/revoke/accept/expire decisions are audited. Team- and project-scoped agents and their sessions now enforce membership access for non-admin principals, and agent/session list APIs hide scoped resources outside the caller's memberships. The static Admin Console can bootstrap tenant scopes, create/select organizations, create teams/projects, create memberships, show active/archived/owner scope state, transfer organization ownership, archive/delete organizations, archive teams/projects, and create/revoke tenant invitations while auto-filling selected org/team IDs into related governance forms. | Full production cross-tenant runtime isolation beyond the current default tenant boundary is not implemented. |
| RBAC | Role-based authorizer guards read, write, run, tool, approval, execution job, audit, and governance admin paths. `admin`, `operator`, `approver`, and `viewer` are recognized. If role headers are absent for a subject, roles are derived from persisted memberships. Scoped agent/session/tool/approval/job paths enforce team/project membership for non-admin principals. Admin-only policy inspection, tool-decision simulation, batch policy test APIs, and policy revision create/list/diff/gate/activate APIs exist; simulation/test/revision actions are written to audit logs. The static Policy Console can review the active policy, simulate one tool decision, run a batch policy test, create validated policy revisions, diff them against the active runtime policy, run default or custom policy gate suites with rollout percentages and optional RFC3339 activation windows, and only activate revisions that passed that gate and are inside the configured window. Policy diffs now render as a change-count summary plus added/changed/removed table, and gate results render rollout, suite, pass/fail counts, activation window, and per-tool expected/actual decisions instead of raw JSON only. Activating a 100% revision hot-swaps the in-memory runtime policy used by simulation, SQL policy checks, and Tool Router decisions; activating a partial rollout keeps the current baseline and applies the candidate policy to a deterministic percentage of sessions by session UUID bucket. Runtime status and audited controls can stop an active staged rollout, preview an aggregate scheduler due plan across policy, approvals, releases, MCP, Codex, and finance export, inspect scheduler orchestration summary/history from audited due-runs, run due scheduled rollout activation for passed draft revisions inside their activation windows, and roll back the active policy to the most recent archived active revision. | Production multi-step rollout orchestration beyond due-plan preview, scheduler history summary, single due-run activation, and active rollback is not implemented. |
| Provider governance | OpenAI-compatible provider transport exists; API keys can be direct env values or Vault references. Admin provider registry APIs are implemented, team-level `provider_access` rows and model allowlist enforcement are implemented for team-scoped agent creation, and session runs resolve stored provider rows, require `active` status, and fail closed for disabled or archived providers before falling back to env/mock. Stored provider configs can enforce daily request and cost budgets. The static Provider Settings form can create/update stored providers with base URL, API key env/ref, budget, and per-request/per-1K-token pricing config, request a provider status approval, activate/disable/archive persisted providers, and run provider configuration health checks. Active OpenAI-compatible providers with `api_key_env` and `base_url` run audited `/v1/models` external probes; providers using `api_key_ref` now resolve through the same Vault secret boundary and run the external probe without exposing secret values in health responses or audit logs. Admins can rotate a provider's bound `api_key_ref` through a dedicated API that removes env-key fallback from the provider config and records previous/new refs in audit history. Provider status changes can be requested through an audited separation-of-duties approval workflow, approved/rejected by a different delegated admin subject, and rendered with pending/last approval state in the static Provider Settings panel. Direct Admin status changes are now explicit emergency changes only: the API requires `emergency=true` plus a non-empty reason and records a `provider_lifecycle_emergency` policy decision in audit history. `GET /api/providers/summary` aggregates provider status/type counts, pending and last lifecycle approvals, emergency lifecycle decisions, credential source coverage, budgeted providers, inactive providers, and governance attention items. `GET /api/providers/policy-gate` now evaluates every provider against readiness blockers and warnings such as inactive status, pending lifecycle approvals, missing credentials, missing base URL, missing budgets, env-key usage, and emergency lifecycle history. `POST /api/providers/policy-gate/run` records an audited gate run with failed/warning provider names and the full report payload, and `GET /api/providers/policy-gate/runs` summarizes latest/recent run status plus stale/missing/failed run attention items. The static Provider Settings panel renders the policy gate, gate run history, and governance summary as compact metric tables before the provider list. | Production provider policy gate workflow beyond the current audited gate run/history, summary dashboard, and lifecycle approval surfaces is not implemented. |
| Vault | Reserved provider and Vault KV v2 HTTP client boundary exist. `GET /api/vault/health` reports reserved/vault provider status, fail-closed configuration issues, and redacted config checks. `GET/POST /api/vault/secrets` and `POST /api/vault/secrets/:id/rotate` provide an audited secret-reference catalog with scoped tenant/team/project metadata and versioned rotation records without returning secret values. `GET /api/vault/readiness` now provides a production-readiness gate across Vault provider health, reserved KMS configuration, registered secret refs, stale rotations, provider `api_key_ref` consumers, MCP connector secret refs, and eval judge profile refs. The static Vault panel renders the readiness metrics, KMS state, attention items, and per-resource checks alongside health and catalog controls. | Partial: production secret value storage and real external KMS/HSM rotation execution are still not implemented, but the readiness gate now exposes blockers instead of leaving them as prose-only gaps. |
| Worker queue | Postgres/in-memory execution queue, Rust `mandoforge-worker` binary, shell worker loop, K8s worker Deployment, lease claims, stale running job reclaim, and retry-or-fail orchestration exist. Jobs persist `attempt_count`, `max_attempts`, and `last_error`; failed worker attempts return to `queued` until the max attempt budget is exhausted, allowing a later lease to retry the same approved work. Redis Streams can be enabled with `MANDOFORGE_EXECUTION_QUEUE_BACKEND=redis` plus `MANDOFORGE_REDIS_URL`; Redis enqueue uses `XADD`, API-backed worker drain uses `XGROUP`/`XREADGROUP`, and completion/final failure confirms messages with `XACK`. Core NATS can be enabled with `MANDOFORGE_EXECUTION_QUEUE_BACKEND=nats` plus `MANDOFORGE_NATS_URL`; approved jobs publish to `MANDOFORGE_NATS_SUBJECT` and API workers drain through a NATS queue subscription for broker-native handoff. The Redis command, RESP parse, NATS TCP publish/message parse, enqueue, readgroup/drain, ack, and in-memory retry paths are covered by tests, and `cargo check -p mandoforge-api --bin mandoforge-worker` passes. The static Worker Dashboard lists memory/Postgres/Redis/NATS execution jobs, status, worker/lease metadata, attempts, last error, and can drain claimable jobs through the API-backed worker route. | Partial: production JetStream-style durability, worker autoscaling, and hard isolation for native worker pools are not enabled. |
| Approval v2 | Approve/reject exists; modify now updates pending tool args, records `approval.modified`, and preserves the approval for later approve/reject. Approvals persist `expires_at`; the expire API records `approval.expired`, and approve/modify fail closed once an approval has expired. Manual approval requests can delegate decisions to an `approver_subject`; non-admin principals must match that subject while admins can override. Approval groups and escalation rules are persisted through Admin-only APIs, `POST /api/approvals/:id/escalate` assigns pending approvals to a configured group/rule, group members can decide those approvals, and non-members are denied. `POST /api/approvals/escalations/run-due` expires overdue pending approvals, advances remaining pending approvals through ordered active escalation rules once each rule's `after_seconds` threshold is due, writes timeline/audit records, and attempts webhook notification delivery for each scheduled escalation. `POST /api/scheduler/run-due` also invokes approval due processing as part of an audited external-scheduler aggregate run, and the K8s skeleton includes a CronJob that calls this aggregate due-run endpoint. `POST /api/approvals/:id/deliver` can send pending approvals to an env-gated webhook via `MANDOFORGE_APPROVAL_WEBHOOK_URL`, resolves delegated approver or approval-group target subjects for fan-out payloads, and writes delivery audit records with target metadata. `GET /api/approvals/notification-routing/summary` now reports configured approval notification channels, pending/delegated/group-routed approval counts, routable versus unroutable pending approvals, approval group and escalation-rule coverage, and routing attention items; the static Approval Governance panel renders that summary. The static Approval Queue shows original args, modified args, delegated approver/group, decision payload, a JSON-path argument diff table, delivery target counts, delivery/escalation controls, and allows pending approval args/comments to be modified before approve/reject. Static Approval Governance can create groups/rules, list them, trigger due escalation runs, and inspect notification routing readiness. | Partial: production multi-channel notification delivery is still limited beyond the webhook fan-out boundary, but routing readiness is now API/UI-visible and fail-closed for pending approvals without targets or channels. |
| MCP Gateway | `mcp.call` is enabled through the Tool Router, uses configured MCP Gateway server allowlists, and is persisted through tool call/event/audit paths. Team-level MCP server registry APIs and persisted per-server tool allowlists are implemented; scoped sessions must use a registered active server/tool before the gateway call proceeds. Admins can import discovered tools from the configured MCP Gateway into a team server allowlist. Admin APIs can patch connector transport/config/allowlist, activate/disable/archive a server with audit records, run audited single-connector health checks against registration status, gateway configuration, gateway allowlists, and gateway reachability, run audited team-level batch health checks, and run due-only scheduled health checks based on connector `config.health_check.interval_seconds`. MCP connector config now accepts normalized `vault:path#key` `secret_refs`, rejects invalid secret paths, keeps secret values out of connector config, and reports secret-ref counts/paths in health checks. Scoped runtime `mcp.call` resolves configured connector secret refs through the `SecretProvider` boundary before MCP Gateway I/O and fails closed without calling the gateway when a ref cannot be read; secret values are not persisted in tool args, timeline, or audit payloads. Due runs persist last health metadata back to connector config for cron/worker-driven supervision. Connector rollout APIs can stage transport/config/tool allowlist/status changes, run candidate health preflight, enforce optional activation windows, apply due rollouts through an audited run, and roll back the last applied rollout to the previous snapshot. `POST /api/scheduler/run-due` runs due MCP health checks and connector rollouts across active teams for external scheduler callers. `GET /api/teams/:team_id/mcp-servers/rollouts/summary` aggregates connector status/transport counts, pending/manual/scheduled/due/expired rollout queues, preflight failures, attention items, and latest rollout history. Disabled/archived servers fail closed through the existing team-scoped `mcp.call` check. Static Admin Console MCP management can load team servers, save config JSON with secret refs, edit registered servers, check single-server or team health, run due health, run due rollouts, trigger discovery import, activate/disable/archive servers, request/apply connector rollouts, roll back applied rollouts, and review rollout summary metrics/attention/history. | Production connector rollout orchestration beyond summary dashboards, due-run application, manual apply, and rollback is not implemented. |
| Codex App Server adapter | Codex CLI adapter exists. An env-gated App Server adapter now exposes Admin-only health, thread, turn, command execution, interrupt, turn polling, stale-turn polling, persisted run-list, trace summary, trace detail, and control-plane summary routes through a `CodexAppServerClient` boundary, with local mock coverage and fail-closed reserved behavior when `MANDOFORGE_CODEX_APP_SERVER_URL` is unset. Thread, turn, command, interrupt, stale poll, and bounded poll responses are persisted in `codex_app_server_runs` for replay/debugging, and polling updates the stored run status/error with audit history. `GET /api/codex-app-server/traces` groups persisted runs into per-turn traces with run/command/poll/error counts, latest status, terminal state, operation sets, and first/last seen timestamps. `GET /api/codex-app-server/traces/:trace_key` returns a single trace's run list, status timeline, errors, and latest response. `GET /api/codex-app-server/control-plane/summary` aggregates configured/reserved state, run/turn counts, stale candidates, pollable turns, status/operation counts, latest activity, and attention items for reserved adapters, failed traces, active turns, and stale turns. `POST /api/codex-app-server/runs/poll-stale` finds stale non-terminal turn runs, polls bounded candidates, and writes per-run plus due-run audit records; `POST /api/scheduler/run-due` invokes the same stale-poll path for external scheduler/Kubernetes supervision. `POST /api/codex-app-server/artifacts/sync` imports App Server artifact descriptors into persisted MandoForge artifacts, `artifact.created` timeline events, and audit logs. Approved `codex.exec` supports `auto`, `cli`, and `app-server` execution strategies; `auto` tries App Server when configured and records a fallback event before returning to CLI on App Server failure. Queue-backed approvals now defer approved `codex.exec` work to execution jobs, and worker drains create App Server threads/turns, persist steering runs, perform bounded turn polling with `codex.task.event` timeline records, retry failed/non-terminal attempts across worker leases, and complete the tool call only after a terminal completed turn. The static Admin Console now has a Codex App Server steering panel for health checks, thread creation, turn creation, turn-scoped command execution, interrupt, bounded run polling, stale-turn polling, artifact sync, persisted run listing, control-plane summary, per-turn trace summary/detail, long-running status metrics, pollable turn labels, and clear reserved/fail-closed responses. | Production App Server control-plane operations beyond current summary, steering, trace, polling, and artifact sync surfaces are not implemented. |
| Evaluation | Eval datasets, cases, and version-bound run records are implemented with deterministic Stage 2 graders for policy decisions, tool allowlist coverage, SQL safety, sandbox path checks, and final-answer required fragments. Runs persist per-case details, pass count, score, and agent version evidence. `grading_policy.kind = "judge"` now routes through either an env-gated `EvalJudgeClient` using `MANDOFORGE_EVAL_JUDGE_URL` or a persisted active `eval_judge` provider profile selected by `grading_policy.judge_profile`. Judge profiles store endpoint/model/timeout and optional normalized `vault:path#key` API key references without resolving or exposing secret values; judge requests and run details include profile/model evidence. Unconfigured judge cases fail closed with explicit evidence instead of silently passing. `POST /api/eval/suites/stage2-regression` creates a default regression suite covering high-risk policy, blocked tools, required tool coverage, read/write SQL safety, sandbox path boundaries, final-answer evidence, and optional external judge scoring. `POST /api/eval/runs/:id/gate` provides a score/status regression gate with failure reasons. `POST /api/agents/:id/releases` still supports direct audited emergency promotion after an eval gate; `POST /api/agents/:id/release-requests` creates pending production promotion requests that persist requested-by, delegated approver, request reason, eval evidence, and an automation policy. Approve/reject endpoints enforce separation of duties and delegated approver matching before recording promoted/rejected decision metadata. `POST /api/agents/releases/run-due` scans pending requests, auto-promotes only system-delegated releases whose automation window is open and score still meets the gate, and auto-rejects expired requests fail-closed with audit records. `POST /api/scheduler/run-due` also invokes release automation as part of the external scheduler aggregate run. `GET /api/agents/releases/summary` aggregates release counts by status/environment, pending/manual/automated queues, expired/expiring/stale attention items, and latest promoted releases by environment. `POST /api/agents/:id/releases/:release_id/rollback` marks promoted releases as rolled back and rejects repeated rollback attempts. `GET /api/eval/runs/:id/drift` compares a run against the previous run for the same dataset and agent. The static console can create judge profiles, bootstrap the Stage 2 suite, create datasets, add JSON cases, run evals, inspect cases/runs, gate a run at 100%, check drift, request manual or automated prod approval, run due release automation, review rollout summary metrics/attention items/latest promotions, approve/reject pending releases, promote a passing eval run to staging/prod, list agent releases, and roll back promoted releases. | Production multi-step release rollout orchestration beyond summary dashboards, due-run activation, approval decisions, and rollback is not implemented. |
| Observability | OTel exporter boundary exists and session event appends now export telemetry events when OTLP is enabled. Exported telemetry attributes classify session/provider/tool/approval/worker/sandbox/codex events as span-like signals and attach counters, status, duration, provider/client/tool IDs, approval IDs, worker IDs, and tool-call counts when present. The HTTP telemetry exporter now emits OTLP-shaped logs, traces, and metrics payloads to `/v1/logs`, `/v1/traces`, and `/v1/metrics` from the same runtime event boundary, with local mock coverage. `GET /api/observability` now powers a static dashboard with telemetry config, session/tool/approval/job status counts, event categories, recent error events, and queue/approval backpressure indicators. `GET /api/observability/remediation/plan` now converts current telemetry/backpressure/error signals into a reviewable remediation plan with auto, manual, and configuration action counts before operators execute anything. `GET /api/scheduler/due-plan` gives operators a read-only aggregate due-run plan across policy rollout, approval escalation, release automation, MCP health/rollout, Codex stale polling, and usage finance export before they execute `POST /api/scheduler/run-due`; `GET /api/scheduler/summary` combines that plan with recent audited scheduler run history, latest status, action counts, and attention items. The static Observability panel renders scheduler orchestration, scheduler plan, and mutable run result separately. `POST /api/observability/remediation/run` records an audited remediation run, executes safe due approval expiration/escalation automation, invokes the Codex App Server stale-turn poller, and returns explicit manual-action markers for worker-drain and failure-triage backpressure that should not be auto-executed from the dashboard. The static Observability panel renders the remediation plan and run result separately. | Broader remediation automation beyond safe approval/Codex due-runs, reviewable plan output, aggregate scheduler due-plan/summary preview, and collector-specific OTLP hardening are not implemented. |
| Cost tracking | `GET /api/usage` aggregates session/event counts, provider requests/responses, prompt/completion/total tokens, configured provider per-request and per-1K-token pricing, tool call status counts, tool runtime, approval counts, and provider budget status over the last 24 hours. `GET /api/usage/trends` compares current usage with the latest persisted rollup or the two latest persisted rollups and returns cost/token/tool-call deltas, 7-day and 30-day run-rate forecasts, provider budget exhaustion projections, top provider by cost, budget pressure counts, and operator recommendations. `GET /api/usage/finance-summary` now composes finance dashboard signals from usage, trends, rollups, budget alerts, alert routes, and scheduled export configuration; it returns forecast highlights, top-provider attribution, rollup freshness, export readiness, recommendations, and finance attention items for budget alerts, missing alert routes, stale/missing rollups, missing export targets, and rapid cost growth. `GET /api/usage/finance-operations/summary` adds an Admin-only readiness and operations layer that combines open/current budget alerts, 24-hour acknowledgement coverage from audit logs, latest finance export and cost-alert delivery audit evidence, rollup/export/alert-delivery status, readiness score, attention items, and deduplicated runbook actions. `GET /api/usage/export.csv` returns an Admin-only audited finance CSV with summary, trend, forecast, provider, budget, budget-forecast, and recommendation rows. `POST /api/usage/export/deliver` builds the same CSV, delivers it to `MANDOFORGE_USAGE_EXPORT_WEBHOOK_URL` when configured, returns reserved/fail-closed status otherwise, and writes audit metadata without persisting CSV content; `/api/scheduler/run-due` can run the same delivery boundary when `MANDOFORGE_USAGE_EXPORT_SCHEDULE` is enabled. `GET /api/usage/alerts` exposes warning/critical provider budget alerts, `GET/POST /api/usage/alert-routes` manages audited webhook/Slack/email alert routes, `POST /api/usage/alerts/deliver` can deliver alerts through configured webhook routes, Slack incoming webhook routes, HTTP email relay routes via `MANDOFORGE_COST_ALERT_EMAIL_RELAY_URL`, direct SMTP relay via `MANDOFORGE_COST_ALERT_SMTP_ADDR` plus `MANDOFORGE_COST_ALERT_SMTP_FROM`, or the fallback env webhook and now records delivery audit metadata, and `POST /api/usage/alerts/ack` records audited human acknowledgement. Static usage UI displays a finance operations panel, finance summary panel, top-level cost metrics, cost trend windows, forecast horizons, projected budget exhaustion, delta rates, top-provider attribution, CSV export/delivery status, provider cost/token breakdowns, provider budget forecast/alert rows, alert route/delivery/acknowledgement status, tool runtime breakdowns, and persisted rollup snapshots.
