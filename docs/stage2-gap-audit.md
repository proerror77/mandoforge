# Stage 2 Gap Audit

This audit maps the PRD v2 Stage 2 target to the current repo state. It is intentionally strict: reserved boundaries count as groundwork, not completed product capability.

## Status Summary

| Stage 2 area | Current state | Gap |
| --- | --- | --- |
| Multi-tenancy org/team/project | Single default tenant remains the runtime scope, but `organizations`, `teams`, `projects`, and `memberships` tables plus Admin-only hierarchy APIs are implemented. Team- and project-scoped agents and their sessions now enforce membership access for non-admin principals, and agent/session list APIs hide scoped resources outside the caller's memberships. The static Admin Console can create/select organizations, create teams/projects, and create memberships while auto-filling selected org/team IDs into related governance forms. | Production tenant lifecycle controls such as archive/delete, invitations, ownership transfer, and tenant provisioning automation are not implemented. |
| RBAC | Role-based authorizer guards read, write, run, tool, approval, execution job, audit, and governance admin paths. `admin`, `operator`, `approver`, and `viewer` are recognized. If role headers are absent for a subject, roles are derived from persisted memberships. Scoped agent/session/tool/approval/job paths enforce team/project membership for non-admin principals. Admin-only policy inspection, tool-decision simulation, and batch policy test APIs exist; simulation/test calls are written to audit logs. The static Policy Console can review the active policy, simulate one tool decision, and run a batch policy test. | Production policy editing and rollout are not implemented. |
| Provider governance | OpenAI-compatible provider transport exists; API keys can be direct env values or Vault references. Admin provider registry APIs are implemented, team-level `provider_access` rows and model allowlist enforcement are implemented for team-scoped agent creation, and session runs resolve stored provider rows, require `active` status, and fail closed for disabled providers before falling back to env/mock. Stored provider configs can enforce daily request and cost budgets. The static Provider Settings form can create/update stored providers with base URL, API key env/ref, budget, and per-request/per-1K-token pricing config, activate/disable persisted providers, and run provider configuration health checks. | Production provider lifecycle management, external health probes, audited key rotation history, and richer provider dashboards are not implemented. |
| Vault | Reserved provider and Vault KV v2 HTTP client boundary exist. `GET /api/vault/health` reports reserved/vault provider status, fail-closed configuration issues, and redacted config checks; the static Vault panel can run this health check. | Production secret storage, secret CRUD, rotation, and scoped secret references are not implemented. |
| Worker queue | Postgres/in-memory execution queue, worker binary, lease claims, and reclaim boundary exist; Redis command/client boundary is reserved. The static Worker Dashboard lists execution jobs, status, worker/lease metadata, and can drain queued jobs through the API-backed worker route. | Live Redis/NATS backend and separate broker worker handoff are not enabled. |
| Approval v2 | Approve/reject exists; modify now updates pending tool args, records `approval.modified`, and preserves the approval for later approve/reject. Approvals persist `expires_at`; the expire API records `approval.expired`, and approve/modify fail closed once an approval has expired. Manual approval requests can delegate decisions to an `approver_subject`; non-admin principals must match that subject while admins can override. `POST /api/approvals/:id/deliver` can send pending approvals to an env-gated webhook via `MANDOFORGE_APPROVAL_WEBHOOK_URL` and writes delivery audit records. The static Approval Queue shows original args, modified args, delegated approver, decision payload, a JSON-path argument diff table, delivery status, and allows pending approval args/comments to be modified before approve/reject. | Production escalation chains and delegated approver groups are not implemented. |
| MCP Gateway | `mcp.call` is enabled through the Tool Router, uses configured MCP Gateway server allowlists, and is persisted through tool call/event/audit paths. Team-level MCP server registry APIs and persisted per-server tool allowlists are implemented; scoped sessions must use a registered active server/tool before the gateway call proceeds. Admins can import discovered tools from the configured MCP Gateway into a team server allowlist. Static Admin Console MCP management can load team servers, create/update allowlists, and trigger discovery import. | Production connector lifecycle management and richer MCP configuration UI are not implemented. |
| Codex App Server adapter | Codex CLI adapter exists. An env-gated App Server adapter now exposes Admin-only health, thread, turn, command execution, and interrupt routes through a `CodexAppServerClient` boundary, with local mock coverage and fail-closed reserved behavior when `MANDOFORGE_CODEX_APP_SERVER_URL` is unset. | Production long-running thread steering UI, artifact synchronization, and CLI/App Server fallback orchestration are not implemented. |
| Evaluation | Eval datasets, cases, and version-bound run records are implemented with deterministic Stage 2 graders for policy decisions, tool allowlist coverage, SQL safety, sandbox path checks, and final-answer required fragments. Runs persist per-case details, pass count, score, and agent version evidence. `POST /api/eval/runs/:id/gate` provides a score/status regression gate with failure reasons. `POST /api/agents/:id/releases` now enforces that a referenced eval run targets the same agent version, is completed, and meets `min_score` before recording a promoted release. `POST /api/agents/:id/releases/:release_id/rollback` marks promoted releases as rolled back and rejects repeated rollback attempts. `GET /api/eval/runs/:id/drift` compares a run against the previous run for the same dataset and agent. The static console can create datasets, add JSON cases, run evals, inspect cases/runs, gate a run at 100%, check drift, promote a passing eval run to staging/prod, list agent releases, and roll back promoted releases. | Judge integrations and production promotion workflows are not implemented. |
| Observability | OTel exporter boundary exists and session event appends now export telemetry events when OTLP is enabled. Exported telemetry attributes classify session/provider/tool/approval/worker/sandbox/codex events as span-like signals and attach counters, status, duration, provider/client/tool IDs, approval IDs, worker IDs, and tool-call counts when present. | Dashboards, retry/backpressure, and full OTLP-native trace/metric encoding are not implemented. |
| Cost tracking | `GET /api/usage` aggregates session/event counts, provider requests/responses, prompt/completion/total tokens, configured provider per-request and per-1K-token pricing, tool call status counts, tool runtime, approval counts, and provider budget status over the last 24 hours. `GET /api/usage/alerts` exposes warning/critical provider budget alerts, `POST /api/usage/alerts/deliver` can deliver those alerts to a configured webhook via `MANDOFORGE_COST_ALERT_WEBHOOK_URL` while failing closed/reserved when unset, and `POST /api/usage/alerts/ack` records audited human acknowledgement. Static usage UI displays top-level cost metrics, provider cost/token breakdowns, provider budget forecast/alert rows, alert delivery/acknowledgement status, tool runtime breakdowns, and persisted rollup snapshots. Provider daily cost budgets are enforced over a 24-hour window before a new provider request starts. | Production dashboard polish, routing rules, and non-webhook delivery channels are not implemented. |
| UI v2 | Static console covers agents, sessions, timeline, approvals, artifacts, tool calls, audit logs, and Admin Console panels for usage, tenant governance, Vault health, policy inspection/simulation, stored providers, eval runs/gates, MCP servers, worker jobs, and governance status. | Full CRUD UI for vault/policy management and production dashboard polish are not implemented. |
